# 渲染与帧性能：最佳实践与常见误区

面向本项目这样一套技术栈的性能参考：**React 驱动 UI + Canvas 2D 画战场 + 可选的 WebGL2 bloom 后处理 + 固定 120Hz 战斗模拟**。渲染发生在 `requestAnimationFrame`（约 60Hz），而战斗模拟以固定步长跑在 120Hz。

核心原则只有一句话：**每帧（以及每个模拟步）都不要分配对象、字符串或数组，也不要做不必要的昂贵 Canvas 状态操作。**

---

## 一、每帧分配：禁止项与替代做法

### 误区 1：“现代引擎够快，每帧分配无所谓”
假的。60Hz × 每帧若干个小对象会持续制造 GC 压力，移动端尤其明显，表现为周期性卡顿（jank）。**“无分配”是该渲染路径的第一优先级。**

### 误区 2：“每帧新建一个小数组没关系”
反例：`for (const offset of [0, Math.PI])` 在每颗投射物每帧都 `new` 一个数组。同屏几十颗投射物时，这就是每帧几十次分配。改为模块级常量，或直接展开成两次绘制。

### 误区 3：“构建一个临时 Point 数组再遍历，很直观”
在“每帧跑一遍”的代码里，`points.push({x, y})` 会逐帧构造数组和对象。应在实例上准备一个**复用缓冲区**，先 `length = 0` 再填充；或者用**游标写入**（`result[writeIndex++] = item`，最后截断 `length`）代替 `push`。

### 误区 4：“`map / filter / sort` 很简洁”
这些都会产生新数组。凡是“每帧/每步”执行的循环，用**就地压缩**（写索引 + 最后 `length = writeIndex`）或直接 for 循环，避免中间数组。

### 误区 5：“字符串/颜色解析每次算一遍就好”
例如把 `#a3b4c5` 转成 `rgba(...)`：`hex.split('').map(...).join('')`、`parseInt` 每次都重算。颜色集合是有限的，用 `Map<string, {r,g,b}>` 缓存一次即可；真正的 `rgba(...)` 只保留必要的一次模板字符串。

### 误区 6：“每次绘制都 `createRadialGradient`”
渐变（`createRadialGradient`）对象相对较重，且 `light()` 这类效果每帧会多次触发。颜色有限，可缓存渐变或至少缓存颜色的解析结果；坐标随位置变化的渐变，可通过“以一个原点 + 平移绘制”复用，或在效果层内控制调用次数。

### 误区 7：“离屏 canvas 越多越好”
每个离屏 canvas 占内存，`drawImage` 也不是零成本。只缓存**真正静态**（背景、路径）或**高频复用**（精灵、光晕）的内容；尺寸要受控，不要为“可能用到”而预先建一堆。

## 二、Canvas 状态管理：真正昂贵的地方

### 误区 8：“`save()/restore()` 只是顺手加上，不贵”
它们几乎不是免费的。每次 `save/restore` 都压栈/出栈整个状态栈；当一条绘制由大量小原语组成（尤其 bloom 模式下还要写入两个目标）时，数千次压栈会有感。应把**共享同一 state 的一组绘制合并**，一次设置 `globalAlpha / lineWidth / strokeStyle / fillStyle` 后连续绘制，再用一次 `restore` 收尾。

### 误区 9：“`shadowBlur` 只是让形状发光”
`shadowBlur` 会对每个形状做一次真实的模糊 pass，是 Canvas 里**最贵**的操作之一。同屏大量“发光”弹体/敌人时几乎主导填充率。用**预渲染的径向渐变精灵 + `drawImage`** 近似，视觉几乎无差，成本一个量级更低。

### 误区 10：“发光和落地阴影是同一件事”
不是。**发光（glow）**是围绕中心的光晕，可用居中精灵替换；**落地阴影（drop shadow / `shadowOffsetY`）**承载纵深信息，替换成居中发光会**破坏观感**。区分二者，只对“发光”做精灵化。

### 误区 11：“`setLineDash` 无副作用”
设置虚线图案本身有成本，且模式数组会随字面量反复分配。把固定图案抽成模块级常量数组；能合并就合并，避免同一帧反复切换 dash 状态。

### 误区 12：“`globalCompositeOperation` 换来换去没问题”
`lighter / multiply / source-over` 之间切换会触发渲染管线状态变更。把**同一种合成模式**的绘制批到一起，避免穿插切换。

### 误区 13：“字体/文本每次设一次没事”
`ctx.font` 和 `textAlign / textBaseline` 每次赋值都涉及字符串解析。对“少数字面文本”可接受；若每帧大量文本，尽量一次设置、分组绘制。

## 三、数学与空间查询

### 误区 14：“用 `Math.hypot` 更精确所以更好”
`Math.hypot` 带溢出保护，是 `sqrt` 里最慢的一路。在**纯阈值比较**（`<=`、`<`）里你根本不需要幅值，用平方距离 `dx*dx + dy*dy` 比较即可，同样精确且免掉开方。只有需要真实长度（归一化、半径）时才保留 `hypot`。

### 误区 15：“取最近目标就 `sort(...)[0]`”
对一个完整结果集排序再取 `[0]`，是 `O(n log n)` 白干。只需**线性扫一遍找最小**的（`O(n)` 且无分配）即可；排序只在真的需要有序结果时才用。

### 误区 16：“每次空间查询都新建并排序结果数组”
提供“传入结果缓冲区”的收集 API，调用方复用同一块 scratch 数组（注意：返回数组不可被持有，只能在一次调用内消费）；对“仅需最近点”的查询用专用的最近点扫描，免得收集全量再排序。

### 误区 17：“空间索引每步全量重建无所谓”
若敌人数量大、且模拟在 120Hz 跑，每步全量重建会是主成本。重建本身属于算法层，改动前先用基准确认它确实占大头；否则优先处理渲染侧更容易见效的点。

## 四、绘制与缓存策略

### 最佳实践：静态内容只画一次
背景、地面网格、路径、方向箭头、分支节点这些**几何固定**的内容，预渲染到一个离屏 canvas，只在尺寸变化（resize）时重建，而不是每帧重绘。

### 最佳实践：动态内容做“离屏精灵 + drawImage”
对有固定形状、只随位置/旋转/尺度变化的实体（塔身、敌人身体、光晕），可预渲染成精灵，每帧只 `drawImage`，避免每帧重新 `beginPath` 大量点。

### 最佳实践：按需走 bloom 通道
bloom 是**全屏**的后处理：每帧要上传场景/emissive 纹理、做两遍降采样模糊和合成。对非发光效果（`bloom === false`）或平台上 GPU 较弱时，应能**回退**到纯 Canvas 2D，且该路径同样可用。不要把 bloom 当成“免费加亮”。

### 最佳实践：限制内部渲染分辨率
填充成本随像素数（`css 宽高 × dpr²`）生长。DPR 上限（如 2 → 1.5）是一个大杠杆；bloom 的 emissive/模糊层已经做了降采样（如 0.5 / 0.25），保持这种“低分辨率效果层 + 高分辨率合成”的思路。

### 误区 18：“WebGL 一定比 Canvas 2D 快”
不一定。全屏后处理引入纹理上传 + 多 pass；在弱 GPU 或高分辨率屏幕上可能反而更慢。**保证回退路径可用**、并让 WebGL 路径只在需要时生效，是更稳妥的策略。

## 五、流程与验证

### 最佳实践：先测量，再优化
用浏览器的 Performance / Memory（Allocation Timeline）面板看每帧 GC、`save/restore` 次数、渐变创建次数。**收益最大的往往很直接**（`shadowBlur`、`save/restore`、每帧数组分配），但应确认，避免为修复问题而引入视觉回归。

### 最佳实践：优化后做视觉抽查
数值等价类改动（矩阵、坐标、平方距离、常量提取）通常无视觉差异，可放心；**替换绘制方式或视觉效果**（如光晕精灵化）必须肉眼复查：光晕是否过大/过小、是否吞掉主体、armed 前后差异是否仍明显、是否出现硬边或闪烁。

### 误区 19：“我改成 `O(1)` 了所以更快”
大 O 只在规模大时才有意义。若单步查询量小、或重建本身不是瓶颈，`O(1)` 化的收益可能被“引入了不可持有的共享缓冲区”这类可维护性风险抵消。**用数据决定优先级**，不要为理论复杂度牺牲清晰度。

### 误区 20：“自动化测试通过 = 没有视觉回归”
单元测试和 smoke 测试只验证“能跑、无异常”，不验证像素。任何改变绘制方式/层级/通道的改动，都要加一次人工视觉检查。
